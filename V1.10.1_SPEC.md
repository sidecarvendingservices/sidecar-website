# Command Center — v1.10.1 Spec: Foundation (UI, Accessibility, Structure)

This is the first of two releases. A read-only accessibility/UX audit
found that the dashboard's core patterns — always-visible forms, dense
tables, an ever-growing Machine Detail modal, div-based "buttons," flat
card hierarchy — won't hold up under the volume of new features in the
original v1.10 list. Rather than build 20 more things on a foundation
that's already straining, **v1.10.1 fixes the foundation first**;
v1.10.2 (separate doc) adds the features on top of it.

Direction for this release, in one line: **an exception-driven operating
system** — show what changed, what needs attention, why it matters, and
the safest next action, everywhere, not just on one tab.

---

## F1. Fix responsive overflow (P0)

**Problem found:** Overview renders 1,918px wide inside a 1,216px
viewport — content is overflowing its own container. At phone width, the
Overview's chart cards force the page to 827px wide inside a 375px
viewport, meaning the whole page horizontally scrolls on a phone.

**Fix:**
- `min-width: 0` on flex/grid children that currently have no explicit
  width constraint (the classic cause of a flex item refusing to shrink
  below its content's natural width).
- Responsive grid tracks (`minmax(0, 1fr)` instead of fixed/implicit
  widths) on the KPI and chart grids.
- `max-width: 100%` on chart containers and canvases.
- Fluid `<canvas>` sizing for Chart.js charts (resize on container width
  change, not a fixed pixel width baked in at render time).
- Fix this **at the component/CSS level**, not with breakpoint-specific
  patches — the same chart component is reused across Overview, Machine
  Health, Google Ads, and Sales Pattern; a systemic fix here prevents the
  same bug from resurfacing every time a new chart gets added.

---

## F2. Machine Detail → dedicated workspace (P0)

**Problem found:** Machine Detail is already a 3,344px-tall modal dialog
with 93 controls in it. The original v1.10 feature list would have
added restocking, planogram, pricing, device controls, contracts, and
expiration batches — all into the same dialog. That's not sustainable.

**Fix: Machine Detail becomes its own page/route, not a modal.**

Sticky identity/status header at the top, always visible while you
scroll:
- Machine name, property, online state, last heartbeat
- Current temperature
- Next service date
- Last HAHA sync
- Primary actions: **Restock**, **Log Service**, **Contact PM**

Below that, local navigation (real tabs, not just a scroll of sections)
into:
- **Overview** — health, sales trend, service priority, active alerts
- **Inventory & Restock** — quantities, runway, expiration batches (v1.10.2
  §9), restock workflow (v1.10.2 §1's original §1 restock button lives here)
- **Assortment & Pricing** — planogram, lane capacity, machine-specific
  pricing and margins (v1.10.2 §6, §7)
- **Health & Controls** — telemetry and gated device commands (v1.10.2 §8)
- **Service & Activity** — service log, tasks, calls, command history
- **Documents** — contracts and coverage (v1.10.2 §11)

This is the structural change that everything else in v1.10.2 depends
on — every original-spec feature that said "lives on Machine Detail"
now has a specific, scoped home instead of getting appended to one
ever-growing dialog.

## F3. Keyboard-operable KPI & drill-down cards (P0)

**Problem found:** KPI and drill-down cards are clickable `<div>`
elements — Overview has 13 of these, Machine Health has 3 — which means
keyboard-only users cannot activate them at all (a `<div>` with an
`onclick` isn't focusable or operable by Enter/Space without extra work
nobody's done here).

**Fix:** every clickable card becomes a real `<button>` or `<a>`, with
an accessible name (not just a visual label — screen reader users need
the same context sighted users get from surrounding layout), and visible
hover/focus states matching the rest of the system's existing focus
styling (which is already strong elsewhere and worth extending here, not
reinventing).

## F4. Dialog accessibility overhaul (P0)

**Problem found:** the Machine Detail dialog (and by extension, likely
every other modal built the same way) has no accessible name, leaves 163
background controls still focusable while it's open, and doesn't return
keyboard focus to whatever triggered it when closed.

**Fix**, applied to every modal system-wide (Add Machine, Restock List,
Add Task, confirm dialogs, etc.), not just Machine Detail once it moves
to its own page:
- `aria-labelledby`/`aria-label` naming the dialog.
- Focus trap — Tab/Shift+Tab cycles only within the open dialog.
- Background inertness (`inert` attribute or equivalent) so
  screen-reader and keyboard navigation can't reach content behind the
  dialog while it's open.
- Scroll locking on the body while a dialog is open.
- Focus restoration — closing a dialog returns focus to whatever
  element opened it, not to the top of the page.
- Escape-to-close is already working — keep it.

## F5. Permissions enforcement mechanism (P0)

**Problem found:** the original spec's device-control, pricing, and
planogram features (v1.10.2 §6–§8) would ship while `role` on
`team_members` remains a cosmetic label with no actual enforcement
anywhere in the app.

**Fix — this release builds the mechanism, even though the gated
features themselves ship in v1.10.2:**
- Formalize `role` into a fixed set: **Admin, Stocker, Receiver, Sales,
  Account Manager** (dropdown instead of free text, on the Team tab).
- Set both your and Vala's records to **Admin**.
- Build the actual gating check — a shared helper (both client-side, to
  hide/disable controls, and server-side in the relevant Functions, so
  it's not just a UI-only illusion of security) that checks the current
  user's role before allowing device commands, pricing edits, planogram
  edits, or other sensitive financial/operational actions.
- **Right now, only Admin exists as a meaningfully-enforced role** — the
  other four are assignable values with no restrictions applied yet
  (same as originally scoped). The difference from the original plan:
  the *enforcement plumbing* ships now, in the foundation release, so
  that when v1.10.2's remote-control and pricing features land, they're
  gated by something real from day one instead of retrofitted after the
  fact.

**Shipped this build:**
- Team tab Role dropdown now offers exactly the five fixed values
  (previously included a free-text-era "Owner" option).
- Client-side `hasRole()` / `requireRole()` helpers added (near the
  `whoami` global in ops-dashboard.html) — v1.10.2 features call these to
  hide/disable controls.
- Server-side `functions/_lib/auth.js` added — exports
  `requireRole(request, env, allowedRoles)`, returns a 403 `Response` if
  the caller (matched via the same Cf-Access-Authenticated-User-Email
  header whoami.js uses) doesn't have an allowed role. v1.10.2's gated
  endpoints call this and return its result immediately if non-null.
- **New migration to run: `migrations/014_role_formalize.sql`** —
  normalizes any existing "Owner" rows to Admin and sets your record
  (`brian.morris298@gmail.com`) to Admin. **Vala's line is commented out**
  in that file — her exact Cloudflare Access login email wasn't available
  to fill in automatically, so edit that line with her real email and
  uncomment it before running, or just set her to Admin from the Team tab
  UI after the migration runs (same effect, no SQL needed).
- **Correction found post-ship (2026-08-16):** `whoami.js` and
  `functions/_lib/auth.js` originally read a plain
  `Cf-Access-Authenticated-User-Email` header — that pattern only applies
  to traditional reverse-proxied origins. Apps on Cloudflare Pages/Workers
  (this site) instead receive a signed JWT (`Cf-Access-Jwt-Assertion`) and
  are expected to verify it themselves. Added
  `functions/_lib/access-jwt.js` to do real signature verification
  (fetches Access's public certs, checks signature/audience/expiry) rather
  than trusting the claim blindly — both files now use it. Requires two
  Cloudflare Pages secrets: `CF_ACCESS_TEAM_DOMAIN` and `CF_ACCESS_AUD`
  (both already set). Confirmed working end-to-end: the header pill now
  correctly shows "Logged in as Brian Morris (Admin)."

## F6. Heading hierarchy + tab semantics (P1)

**Problem found:** no page or section titles use `h1`–`h6` anywhere;
tab-like controls (the sidebar nav, subnavs, the Tasks/Calls/All toggle,
etc.) have no ARIA tab semantics.

**Fix:** establish a real document heading hierarchy (page title as
`h1`, section titles as `h2`/`h3` as appropriate) and proper
`tablist`/`tab`/`tabpanel` roles with keyboard arrow-key navigation
between tabs, wherever tab-like UI exists.

---

## F7. Accessible charts (P1)

**Problem found:** the three Overview charts are unlabeled `<canvas>`
elements with no accessible summary — a screen reader user gets nothing
from them at all.

**Fix:** every chart gets an accessible name, a concise text summary of
what it shows, and a "View data table" toggle that renders the same
data as an actual `<table>` — satisfies both accessibility and gives
sighted users a precise-numbers option charts can't provide.

## F8. Products page structural overhaul (P1)

**Problem found:** the Products table currently renders 73 `<select>`
elements, 1,332 total `<option>`s, and roughly 3,000 DOM elements, with
96 focusable controls all live on screen simultaneously — many of those
selects unlabeled. This is both an accessibility failure and a real
performance/usability problem regardless of ability.

**Fix:**
- Category displays as **plain text** by default; the `<select>` only
  appears when you click into a row to edit it (not one live select per
  row, all the time).
- Row-level editing moves into a **drawer** (click a row → side panel
  with full detail/edit) instead of inline-editable cells sprawled
  across a wide table.
- **Bulk editor** for category tagging specifically, since that's the
  one action you're likely doing to many rows in a sitting.
- **Pagination or virtualization** so the DOM never renders more than a
  screen's worth of rows at once.
- Real **sorting and filtering** on the table (name, category, margin,
  machine count).
- This is the structural foundation v1.10.2 §7 (per-machine pricing
  dialog) builds on top of — that dialog was already scoped as a
  drill-down from a table row, which fits this redesign directly.

**Shipped this build:**
- Category is now plain text in the table; editing happens by clicking
  the row, which opens a new right-side **drawer** (`openDrawer()` — a
  CSS variant of the existing accessible modal, same focus trap/
  inertness/restoration from F4, just docked to the right edge instead
  of centered).
- Drawer combines category editing + "Log a Purchase" + cost history in
  one place, replacing the old modal that only had the latter two.
- **Bulk editor**: checkbox per row, a bar appears once anything's
  selected with a category dropdown + Apply, sets the category on every
  selected product in one action.
- **Sorting**: every column header is a real button with `aria-sort`,
  toggles ascending/descending (Product, Category, In Machines, Current
  Cost, Price, Margin).
- **Filtering**: category dropdown (all categories + "Uncategorized") on
  top of the existing name/ID search.
- **Pagination**: 25 rows per page instead of rendering the whole
  catalogue at once — Prev/Next control appears once there's more than
  one page.
- Net effect: a product row now renders one checkbox + one text cell
  (no per-row `<select>`) instead of a live category dropdown on every
  row — the DOM-bloat root cause the audit flagged is gone at the
  source, not just paginated around.

## F9. Contrast fixes (P1)

**Problem found:** inactive tab/filter text measures roughly 4.08:1
contrast; descriptive/secondary text measures roughly 4.25:1 — both
below the WCAG AA threshold for normal text.

**Fix:** raise both to at least **4.5:1**. Likely a small palette
adjustment (darkening the "inactive"/"muted" text color slightly) rather
than a redesign — worth a quick pass across the whole color system to
catch anywhere else the same muted tone is reused.

---

## F10. Touch target sizing (P1)

**Problem found:** several filter controls measure about 26px tall;
sidebar and toolbar buttons are typically 34–39px — both below a
reliable touch target size, which matters most for the field workflows
(Restock List, the future Troubleshooting panel) this dashboard is
increasingly meant to be used from on a phone or iPad.

**Fix:** adopt a **44×44px minimum** interactive target across the
system, prioritizing anything used in the field first (Restock List
quantity inputs and buttons, QMOS entry, the future device-control
panel).

## F11. iPad layout — corrected approach (P1)

**Note:** this revises the original v1.10 §13 plan, which proposed
forcing the full desktop sidebar layout at iPad widths. The audit
specifically flagged that approach as wrong: **iPad navigation
currently hides Sales and Marketing at certain widths**, and forcing
the desktop sidebar across the 768–1180px range would make that worse,
not better, on top of fighting portrait orientation.

**Corrected fix:**
- Keep the responsive/adaptive behavior through the iPad range —
  **don't** force the desktop sidebar layout at 768–1180px.
- Instead, make sure nothing that should be reachable (Sales, Marketing,
  and everything else) gets hidden or requires horizontal scrolling to
  find at those widths — the goal is "nothing important is hidden or
  clipped," not "pixel-identical to desktop."
- Apply F10's touch targets here specifically, since this is exactly the
  width range/use case (standing at a machine, or holding an iPad during
  a site consultation) where touch precision matters most.
- Test on real iPad widths (both portrait and landscape) as part of
  verification, not just Chrome DevTools' generic tablet preset.

**Shipped this build:**
- Checked the actual compact/overflow breakpoint: nav collapse into the
  "More ▾" menu is gated at `max-width: 700px`, well below iPad portrait
  (~768–834px) and landscape (~1024–1180px) — so Sales/Marketing were
  **not** actually getting hidden into "More" anywhere in the iPad range
  at current code (this may have been true against an earlier build the
  audit ran against, or was a side effect already fixed by the F1/F2 nav
  work — either way, verified clean now).
- What genuinely was missing at iPad widths: `.tab-btn` (and the "More ▾"
  button, which shares that class) had no explicit touch-target sizing —
  every other interactive control got 44px min-height in F10, this one
  slipped through since it's not a `.btn`/`.subnav-btn`. Fixed the same
  way.
- Real-device testing (not just DevTools' generic tablet preset) is still
  worth you doing a pass on once this is live — flagging as a manual
  verification step for F20 rather than something I can confirm from here.

## F12. Shared UI & CSS direction

A set of system-wide patterns to establish now, before v1.10.2 adds more
surfaces that would otherwise each reinvent (or skip) them:

- **Consistent page header** on every tab: page title, a one-sentence
  purpose line, a freshness/status indicator, and one clear primary
  action — replacing the current flat "card title" treatment that makes
  every section look like a similarly-weighted white box.
- **Move persistent, always-visible creation forms into a modal or side
  drawer** — currently Machines, Properties, Team, Contacts, Expenses,
  Sales, Backstock, and QMOS all keep a form permanently on-screen
  taking up half the layout. Quick Add already established the right
  pattern (button → modal); extend it to these sections instead of
  maintaining two different creation patterns side by side.
- **Reserve cards for summaries and grouped concepts** — not a card
  around literally every section, which is a big part of why the whole
  dashboard currently reads as flat.
- **Standardized table behavior**: sticky header row, sticky
  identifier column (name/product/machine stays visible while scrolling
  right on a wide table), sortable headers, column filters, saved views
  (see F19), contextual row action menus, and proper responsive overflow
  instead of ad hoc per-table handling.
- **Row action menu** replacing repeated inline Edit/Remove/Delete
  buttons — but every action inside it still needs a **contextual
  accessible name** (e.g., "Edit Brian Morris," not just "Edit" three
  times on a page with a screen reader announcing the same word
  repeatedly).
- **Distinct visual states** for critical failure, warning, due,
  informational, success, and acknowledged. Right now the same red
  treatment is used for low margins, missing contracts, service urgency,
  and device failure — visually flattening genuinely different severity
  levels into one color.
- Chart responsiveness fixed at the component level (see F1), not with
  scattered breakpoint patches.

## F13. Content & terminology corrections

A few labels currently used in the dashboard could create real financial
confusion if left as-is, especially once more people (and eventually
non-admin roles) are looking at these numbers:

- **"Net Sales"** currently means gross sales minus COGS and processing
  fees — that's actually closer to **gross profit / contribution
  profit**. "Net sales" conventionally means revenue after discounts,
  refunds, and allowances — not after COGS. Rename to avoid the
  mismatch (e.g., "Gross Profit" or "Contribution Profit" — final
  wording to decide together, see the Metric Dictionary in F15).
- **"Net Profit"** should be renamed **"Tracked Operating Profit"**
  unless/until it actually includes every relevant operating expense,
  depreciation, interest, and tax — calling it "Net Profit" implies
  more completeness than the current calculation delivers.
- **Commission display** currently mixes a rolling 30-day window with a
  full calendar month's commission behind a disclaimer — pick one
  consistent model instead: either show **recognized commission for
  completed months only**, or clearly label it as **estimated accrued
  commission for the selected window**. Don't blend both under one
  number with a footnote.
- **Header "History"** button currently only shows last-sync
  timestamps — rename to **"Data Syncs"** or **"Integration Status"**,
  and add a separate, real **"Activity History"** for actual business
  changes (see F17, Activity & Audit History) — those are two different
  kinds of "history" currently conflated under one button.
- **"Sync"** button renames to **"Sync Data"**, and should show "Last
  synced X min ago" plus a clear success/error state, not just fire an
  action with no persistent status.
- **Negative Backstock alert** currently reads as a generic
  "Follow-up" — replace with something actionable: **"Inventory
  deficit · 1 unit"** with direct buttons for **Record purchase** or
  **Adjust inventory** (ties directly into the Shrink/Adjustment feature
  in v1.10.2 §5).
- **Contextual explanations instead of a bare dash** — e.g., "Not
  enough sales history" reads far better than an unexplained "—" for a
  velocity/days-remaining calculation that simply doesn't have enough
  data yet. Apply this pattern anywhere a dash currently stands in for
  "can't calculate this."

## F14. Machine creation — remove redundant data entry

**Problem found:** Add Machine currently asks for host, address,
property-manager name, phone, and email — even though Properties and
Contacts already hold most of this. The property itself gets assigned
separately, afterward, in the table.

**Fix:**
- Add Machine flow starts by **selecting the Property first**.
- Address, contacts, account manager, and stocker **inherit
  automatically** from that property once selected.
- An explicit **"Use different details for this machine"** override is
  available for the genuine edge case (e.g., a machine at a location
  with a different on-site contact than the main property record), but
  it's opt-in, not the default data-entry path.
- This also **prevents duplicate property-manager records** — today,
  typing a PM's name/phone/email again per machine risks creating a
  near-duplicate Contact instead of reusing the existing one.
- **Also flagged for review, not necessarily changed yet:** "Assigned
  Operator," "Account Manager," and "Stocker" currently overlap without
  clearly documented responsibilities. Worth a short conversation to
  either define what each one actually governs, or remove "Assigned
  Operator" specifically if it doesn't drive any distinct workflow
  today — cutting an ambiguous field is often better than keeping it
  around undefined.

## F15. Metric Dictionary

A single reference definition for every calculated number in the
dashboard, so "what does this number actually mean" has one authoritative
answer instead of living only in scattered code comments. For each
metric: **definition, calculation, source data, period/window, and
freshness** (when it was last computed/synced).

Metrics to define at minimum: Gross Sales, Net Sales / Contribution
Profit (renamed per F13), Operating Profit (renamed from Net Profit per
F13), COGS, Margin, Runway (Backstock sourcing), Sell-Through Velocity,
Service Date (and the expiration-driven early-pull rule), and Commission
(recognized vs. accrued, per F13).

This becomes both a UI reference (a tooltip or dedicated glossary page
users can check) and an internal engineering reference so future
features compute these consistently instead of each new tile inventing
its own version of "margin."

## F16. Data Health & Freshness

A dedicated view showing, per integration (HAHA, Google Ads, Google
Analytics, and Zoho once it exists):
- Last **successful** sync
- Last **attempted** sync (even if it failed)
- Stale-data threshold and whether it's currently exceeded
- Recent failures, with enough detail to know what to check
- Partial-data warnings (e.g., HAHA returned some machines but not all)

Paired with a **Data Quality view**: a checklist-style surface for
missing costs, missing capacity, unassigned machines, missing/unresolved
contracts, and unresolved negative inventory — the operational
housekeeping items that are each individually small but easy to lose
track of without one place that lists all of them together.

---

## F17. Activity & Audit History

A real audit log, separate from the sync-timestamp "History" button
(renamed per F13). Records **who** changed pricing, planograms,
inventory, expenses, permissions, contracts, device state, or resolved
an alert — with **before/after values** and outcome (success/failure).

This is explicitly called out as a prerequisite for the remote
device-control panel (v1.10.2 §8) — a "restart this machine" button
needs a trustworthy record of who pressed it and what happened,
especially once non-admin roles exist down the line.

---

## F18. Command Center Action Center

A unified, prioritized queue — effectively the new front door of the
dashboard — surfacing every open item that needs a human decision:
machine outages, temperature alerts, upcoming/overdue service dates,
inventory deficits, low Backstock runway, nearing expirations, missing
receipts, missing contracts, data-quality issues (from F16), low
margins, and overdue tasks.

Each item carries: **severity, age, owner, source, a recommended next
action, and its resolution state.** This is the concrete expression of
the "exception-driven operating system" direction this whole release is
built around — instead of you cross-referencing six tabs to figure out
what needs attention today, one view aggregates it.

---

## F19. Global Search, Filters & Saved Views

- A single search reaching across machines, properties, contacts,
  products, and tasks.
- Persistent date/property/machine filter state (doesn't reset every
  time you switch tabs).
- Saved views for common contexts, e.g.: **Today**, **Needs Attention**,
  **Field Visit**, **Inventory Purchase**, **Financial Cleanup** — each
  a pre-configured filter combination rather than something you rebuild
  by hand every time you're in that mode.

## F20. Accessibility acceptance criteria (WCAG 2.2 AA)

Formal checklist this release needs to satisfy before it's considered
done — not aspirational, an actual gate:

- Real page and section headings (F6)
- Keyboard-operable cards, tabs, tables, menus, and (later) planogram
  editing
- 44×44px minimum touch targets (F10)
- 4.5:1 minimum contrast for normal text (F9)
- Status communicated by more than color alone (F12)
- Named dialogs with focus trap, Escape-to-close, background inertness,
  and focus restoration (F4)
- Proper labels on every search box, date range, filter, and inline row
  control
- Contextual accessible names for repeated actions (F12)
- Accessible chart summaries and data-table alternatives (F7)
- Announced loading, success, validation, and failure states (screen
  reader live regions, extending the polite live regions already
  working today)
- 200% browser zoom / text reflow without horizontal page scrolling
- Reduced-motion support (`prefers-reduced-motion`)
- No drag-only interactions — the future planogram editor (v1.10.2 §6)
  specifically needs a non-drag way to assign a product to a lane

**What's already working and should be preserved, not redone:** the
skip link, nav/main landmarks, strong existing focus styling, the
semantic Quick Add menu behavior, labeled primary form fields, polite
live regions, and Escape-to-close on dialogs. This release extends those
patterns everywhere they're currently missing, rather than replacing
what's already correct.

## F21. Card content-height alignment across variable-length descriptions (added mid-build)

**Problem found (screenshot, mid-build):** on paired cards in the same
grid row (e.g., Overview's "Sales & Profit Trend" next to "Expense
Breakdown"), the actual chart/content start position drifts vertically
between the two because one card's description text wraps to more lines
than the other's. Titles themselves line up fine — it's everything below
the description that doesn't. This got more visible once F10's 44px
touch targets made the Trend card's Month/Week/Day toggle row taller
than the Expense card's plain title row.

**Fixed already, this pass:** the "View data table" toggle (F7) no
longer contributes to this — it's now pinned to a consistent
bottom-left position on each chart card via `position: absolute`, so its
placement no longer drifts with content height above it.

**Still open — deferred on purpose:** fully normalizing content-start
height across arbitrary card pairs dashboard-wide (not just this one
Overview pairing) is a real design-system task, not a quick CSS patch —
description lengths vary a lot across dozens of unrelated card types
(KPI tiles, forms, chart cards), and a blanket fix risks introducing
awkward empty space in cards that don't need it. Worth its own pass as
part of F12's page-header standardization, once that's underway and the
common header structure it introduces makes the variable-height problem
easier to solve consistently rather than one card pair at a time.

## v1.10.1 build order

1. **F1 — Fix responsive overflow.** Blocks accurate work on everything
   else, since you can't properly evaluate a redesign on a page that's
   already overflowing its container.
2. **F12 — Shared UI/CSS direction** (page header pattern, form→modal
   migration, standardized tables, status-color system). Foundation the
   rest of this release's UI work builds on.
3. **F3, F4 — Keyboard-operable cards + dialog accessibility overhaul.**
   Apply across existing surfaces first; new surfaces built later this
   release (Action Center, etc.) inherit these patterns from the start
   instead of needing a retrofit.
4. **F6, F7, F9, F10 — Headings/tab semantics, accessible charts,
   contrast, touch targets.** Bundle as one accessibility pass across
   existing pages.
5. **F2 — Machine Detail → dedicated workspace.** The biggest single
   change in this release; do it once the shared patterns above exist so
   the new workspace is built with them from day one, not against the
   old dialog patterns.
6. **F8 — Products page structural overhaul.** Same reasoning as F2 —
   large surface, worth doing with the shared patterns already in place.
7. **F14 — Machine creation redundancy fix.** Naturally pairs with F2
   since both touch the machine data model/entry flow.
8. **F11 — iPad layout correction.** Do after the shared responsive
   patterns (F1, F12) exist, so this isn't fighting the old CSS.
9. **F15, F16, F17 — Metric Dictionary, Data Health & Freshness,
   Activity & Audit History.** These three are closely related
   (definitions → data trust → accountability) and share a lot of the
   same "system status" surface area — reasonable to build together.
10. **F18 — Command Center Action Center.** Needs F15–F17 to have real
    data to aggregate (severity/source/recommended-action data is more
    meaningful once the underlying systems it pulls from exist).
11. **F5 — Permissions enforcement mechanism.** Deliberately placed
    near the end of this release, right before v1.10.2 — this needs to
    be solid and tested before v1.10.2's gated features (remote device
    control, pricing edits, planogram edits) start relying on it.
12. **F19, F20 — Global Search/Saved Views, and a final formal
    accessibility acceptance pass.** F19 last since it's additive and
    benefits from every other page redesign being finalized first; F20
    as the closing verification gate for the whole release.

Once this release ships, v1.10.2 (separate doc) adds the actual new
features on top of it — see that doc for the full feature list and its
own build order.
